# R3：经过验证的返回值合同不是完整效果合同

[English](r3-effect-boundary.md) · [源执行顺序](r3-source-schedule.zh-CN.md) · [剩余工作](r3-remaining-work.zh-CN.md)

**真实反例表明，仅凭当前 `ScalarEffect` 返回值合同，不能推出一般目标重放成功。** 这是接口／证明义务，不是求解器能力问题，也不能通过假设目标成功来绕过。

测试与验证共用的[实现](../crates/cordis-kernel/tests/support/replay_effect_boundary.rs)实现 `ScalarEffect`，并证明精确的 `Add(1)` 返回值合同。同时，它持有真实编号分配器和目标值的引用，在第二次调用时，先对该共享值执行额外的 `Add(0)`，再返回计算结果。`Add(0)` 不改变数值，但会增加尚未恢复的逆操作深度。当前 trait 的返回值后置条件没有禁止这次写入。

[运行案例](../crates/cordis-kernel/tests/replay_effect_boundary.rs)使用原 registered root 解释器和 `Source::instantiate`：

1. 源和目标的标量初态均为 `(value = 5, depth = 0)`。
2. 源调用返回模型规定的结果，成功写入 `(6, 1)`；重放前目标仍是 `(5, 0)`。
3. 目标运行同一个保留函数。计算过程中，额外写入使目标在正常落地前变成 `(5, 1)`。
4. 正常落地检测到干扰并拒绝，managed 队列没有添加这次被拒绝操作的逆操作。隐藏写入不会因此自动得到登记或恢复。

复现不需要并发线程，也不依赖未经验证的 fixture 实现。以下脚本先验证 Cargo 实际编译的同一份实现，再运行案例：

```sh
bash scripts/check-r3-effect-boundary.sh
```

正向证明建立的是实现的返回值合同；运行测试复现这一具体源／目标组合，并未声称整个运行案例已经符号化证明。既有的拒绝与逆操作所有权合同仍然有效，不会把失败误报为成功。

## 对论文到代码 refinement 的影响

论文恢复解释要求：所计入的操作状态变化和读取，与可执行实现对应。如果回调还能额外写共享对象，或者持有未随目标搬移的引用，那么纯返回值模型加上正确的 managed 写入仍然不够。完整观察一次源历史，也不能推出回调再次执行时不会产生新的额外效果。

已选择并开始实现[受控效果边界](r3-controlled-effects.zh-CN.md)：恢复定理涉及的状态必须经由审查过的操作接口访问，包含声明读写范围、身份搬移和真实历史／owner 来源。实现方向是统一约束论文范围内的插件访问，而不是为任意回调添加纯度标记。首步已把封闭数据指令接入原解释器、真实锁内提交和清理队列，并在受控重放入口拒绝回调指令。通用插件 API 继续保留显式的回调／环境合同，不能因内置操作已受控就推断所有扩展实现都具有相同读写范围。

此发现**没有**缩小 R3 验收标准，没有宣称任意回调已验证，也没有关闭 R3-A/B。解决效果边界后，仍需完成完整生命周期调度器和最终式 (55) 组合。
