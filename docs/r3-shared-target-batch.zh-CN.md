# R3：共享对象与真实多调用目标执行

[English](r3-shared-target-batch.md) · [目标调用](r3-target-execution.zh-CN.md) · [R3 剩余工作](r3-remaining-work.zh-CN.md)

显式启用的重放路径现在可以初始化共享目标服务，通过真实 native provider 发布它们，再执行一组保留的 root 函数。不同服务名访问同一源对象时，会复用同一个目标对象。返回的报告和清理 owner 均来自实际目标执行，也保留失败调用中已经成功的操作前缀。

**这是 native 目标执行的组成部分，R3 仍未完成。** 当前还没有自动导出完整的剩余源调度，也没有证明每个满足合同的源区间都必然能在目标端成功执行。

[源驱动标量落地](r3-scalar-landing.zh-CN.md)现已检查真实目标输入，并证明准入有效且落地状态未变时，产生对应结果及实际入队逆操作。这关闭了基本操作的一项义务；跨 batch 自动推出输入和干扰条件仍未完成。`ScalarEffect` 的返回值合同本身不代表计算期间不会修改共享状态。

现会在登记前检查来源连续性，在 Finish 或下一次调用前核对真实标量目标输入。
无失败返回可证明实际输入、结果、分支和严格逆操作状态相等。调用后的不一致会保留报告与
清理所有者；这不是写入前的原子守卫。混合 `run_controlled` 路径继续保留已有合同。

## 实际执行路径

1. 真实 Journal 分配器为每次分配生成可执行名称。分配器的持久凭据把编号绑定到带 Journal 的分配地址；Journal 内另有规范化凭据，保证同一次分配不会对应两个名称。标量和 typed 对象的克隆共享身份，typed 对象退休后仍保留身份。
2. `run_replayable_root` 从返回 owner 队列中实际保留的逆操作捕获操作数与身份，不重新读取可能已经改变的服务，也不复制逆操作权限。
3. `Bank::bind` 按源分配地址查找条目。首次使用才创建真实目标标量或 typed 对象及共享服务槽位；后续使用复用该条目，包括标量深度非零的后续操作数。如果首次操作数已经有未完成的标量历史，则明确拒绝，因为此前的目标操作尚未执行。typed 目标使用自身的 head/revision 历史。
4. `batch::run` 从实际 Call 位置导出时间顺序置换、检查共同源流，再准备端口绑定，再注册真实 provider，执行其 Begin、空 managed root、服务发布与 Finish。随后通过 `Source::instantiate` 和现有 registered root 解释器逐个运行保留函数，并实际执行 Finish。
5. 每次调用保留真实 action/work 来源、报告和 `RecordedExecution`；provider 也保留报告与 owner。中途失败时返回已完成前缀，以及已经创建的失败调用 owner；不回滚、不丢弃逆操作、不把未完成清理当作成功。注册或 Begin 失败时，如已创建注册项，也会返回其 ID。

可执行入口为 [`reversible_value/managed/replay/batch.rs`](../crates/cordis-kernel/src/reversible_value/managed/replay/batch.rs)。调用者保留真实调用产生的 `Source`，提供目标 runtime、源命名 Journal 和起始 anchor/work 编号，再检查返回的 `failure`、`calls`、`providers` 与 `bank`。后续可以使用已有的退出、清理、重试和释放接口。anchor/work 编号耗尽会被检查。

## 已证明合同及边界

| 合同 | 结论 |
| --- | --- |
| `AllocationIdentity::same` | 在共同的已认证命名域内，可用编号比较相等，当且仅当带 Journal 的源分配地址相同。编号耗尽返回无身份，不复用旧编号。 |
| `Input::wf` 与捕获 | 保留的身份、操作数、程序位置和队列票据，关联同一真实源步骤及其保留的逆操作。 |
| `Bank::bind` | 每个源地址只有一个条目，已有目标条目保持不变，成功结果对应请求的源分配；首次目标初值来自该真实操作数。 |
| `Batch::actual_prefix` | 返回调用是自动排序后保留函数的有序前缀，`order` 映射回源输入下标，经过真实目标解释器，具有真实报告和已保留逆操作；所有调用完成凭据属于对象表的实际目标 Journal。 |
| batch 成功返回 | 所有提供的函数都获得了实际成功调用报告，没有虚构成功目标步骤。这是实际执行成功时的结论，还不是从源执行推出目标必成功的定理。 |

当前构造器使用一个私有进程内分配器。证明接口仍要求收集的源输入具有**共同的已认证命名域**（`supported_namespace`）；组装任意跨 Journal 来源时，自动消除这一前提仍待完成。编号不能作为另一个进程、持久化执行或独立分配器的可移植身份。

分配器权威映射、Journal 规范化映射、源步骤和对应证据均会擦除。运行时每次 Journal 分配增加一次原子编号分配和一个身份句柄；显式重放捕获还会保留实际操作数和共享目标句柄，普通调用不保留重放输入列表。身份编号耗尽不阻止普通操作，但 batch 无法准备没有名称的输入。

## 当前执行范围

batch 支持有限 root 函数，其声明依赖必须能从已捕获成功步骤的操作数初始化。对于 root 自身的 publication、缺失的依赖操作数、不匹配的操作数类型，以及同一端口被重新绑定到不同源对象，会明确拒绝。不同端口可以共享同一对象。

调用按照[源计划器](r3-source-schedule.zh-CN.md)导出并检查的**实际源 Call 顺序**执行，provider 在调用前准备好；这还不是完整原始 Journal 调度。目标端已有服务或外部并发写入可能改变选择或导致实际调用失败。准确返回失败具有运行价值，但不能替代论文中“剩余执行存在”的证明。

剩余证明包括：从实际源命令与所有权导出完整选定生命周期调度，维持目标当前状态对应并推出原语成功，搬运动态绑定及 owner publication，组合 Child、退出、清理／重试与 Unload。一般目标分配的单射性和完整 action/work/inverse 对应，也需要接入这一源到目标模拟。它们仍属于 R3-A/B；Mixed/Fresh、Node 和式 (55) 保留原有 R3-C/D 验收义务。

## 集中验收

[`reversible_value/managed/replay.rs`](../crates/cordis-kernel/tests/managed_replay.rs) 的运行案例覆盖：

- 两次真实调用、四个服务名、两个共享标量／typed 对象；
- 由真实操作产生的目标标量深度 `0 → 1 → 2`；
- 提前清理失败、保留依赖与 owner、清理后续调用、成功重试并恢复初值；
- 第二次调用失败时保留两个真实 owner 及已经成功的操作前缀；
- 自动纠正倒置输入，拒绝混入其他源流、缺失的必要前序操作及变更的源端口绑定；
- 区分不同 Journal 分配，typed 对象退休后身份保持稳定。

这些运行和证明案例有明确范围。联合开发检查以匹配源码的[开发记录](development-report.json)为准；这些检查本身不代表 R3 完成、全量负控或发布验收。
