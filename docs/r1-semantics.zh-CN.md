# R1：连接到可执行代码的上下文解释

[English](r1-semantics.md) · [论文里程碑](paper-refinement-roadmap.zh-CN.md)

R1 为已经验证的同步解释器建立了明确的**有限、严格部分上下文解释**。创建子插件的父组件、续体、真实服务值和实际捕获的逆操作，现在具备连接到 Rust 执行代码的统一语义合同。R1 在这个解释下完成；这不意味着运行时已经等价于论文原文的无限制总函数解释。

原文审计保持独立，尤其是第 28、47、55、56、57 项保留原来的状态。下面明确列出语义修订，不把它们当作已经证明原文的新增前提。

## 统一解释

输入载体包含指定接口下所有有限、类型正确、结构良好的注册表，而不是某条执行历史中的成功状态。操作返回 `Option<Landed>`：缺失绑定、provision 冲突和非法 Child 名称仍然未定义。原生 API 保留实际的 `Result` 错误；分配容量和重复声明检查也属于精确表示的一部分。

`FreshDriver` 的可执行语言包含 Unit、Provide、Xor 和动态分配身份的 Child。注册前验证代码库；有限的蓝图依赖关系支持嵌套子组件，续体保留原来的程序索引。通用语义合同支持具有已证明标量逆操作定律的类型化 primitive 库。原生 u64/Xor 库通过 `library_theory` 提供这些证明，无需调用者假设它们成立。

统一上下文直接读取执行器的真实存储：

| 字段 | 表示及解释 |
| --- | --- |
| 注册表 | 身份、父子关系、retire 标记、阶段、声明、已提交的 provider |
| 服务 | 每个已注册 owner 的真实键值表，包含非 Active 阶段的表 |
| 根和当前迭代器 | 已验证的蓝图和程序位置，由同一个动态名称语法解释 |
| 累积逆操作 | 实际保留的 receipt，按逆序解释为严格部分函数 |
| 分配器 | 单调递增的下一个身份，以及机器容量限制 |

这里不存储“所有数学函数”的自引用集合，而是用有限的代码与 receipt 数据解释函数字段。比较覆盖**任意测试上下文**，包含逆操作失败；不会仅凭日志编号相同推断函数相同。解释和证明是 ghost 代码，不增加运行时依赖，也不要求 Node.js。`inverse_at` 只读查看真实 receipt。

## 明确标注的修订

| 修订 | 对应原文 | 处理方式 |
| --- | --- | --- |
| R1-CONTEXT | 定义 28，定义 48–50 中的函数字段 | 采用有限的代码和日志表示，不声称满足原文无限制的 `μΓ. Γ × (Γ → Γ) × Σ` 等式；保留现有对角线障碍证明。 |
| R1-DOMAIN | 定义 29–30、48、52、55–56，引理 57 | 使用带接口索引的严格部分 Component 合同：准入观察控制信息和声明内的服务值，恢复比较服务观察；失败显式保留，证明实际返回的逆操作。 |
| R1-FIELDS | 公式 (54)，迭代器和累积器字段 | 将根、当前代码和实际日志解释为任意输入上的严格部分函数，证明执行存储与源语义一致；不宣称已经分类任意回调或所有观察等价程序。 |

区分准入和恢复有明确的必要性。Child 创建成功后执行实际逆操作，会留下已经 retire、表为空、但仍注册的子组件。服务观察恢复了，但这个子组件声明的 provision 仍会阻止在**另一个新鲜名称**上的创建。`no_single_recovery_and_admission_relation` 证明：不存在一个关系，既把这次逆操作算作恢复，又保留上述严格 Child 定义域。因此，仅把控制字段加入服务值相等关系，无法同时修补两个要求。

## 已证明的内容

`guarded_components::member_is_component` 从最小构造语法和标量 primitive 定律推出语义合同。量化范围是完整合法输入载体，不预先假设某条执行成功。合同覆盖：

- 成功和失败定义域的精确对应。非声明范围的服务值可以不同；在准入控制一致时，声明内输入决定值读取、结果、续体和 receipt。
- 正向写入范围、输出的类型与有限性，以及实际返回的逆操作对服务观察的恢复。
- 对任意合法测试输入，实际捕获的逆操作只要有定义，就保持载体和逆操作写入范围。
- 实际续体和动态创建的子组件根，继续满足同一个语义合同。

`MixedDriver::root_component` 为每个实际安装的根建立合同，包含创建子组件的父组件。`reified_representation` 将真实存储与源配置关联；`function_correspondence` 在任意输入上比较根、当前迭代器和完整累积逆操作。`reified_insertion_domain` 纳入真实分配容量、代码验证、重复声明和注册表冲突守卫。

可执行调用者 `run_inspected` 把这些结果组合起来：接收代码库和命令，从空机器构造源执行历史，返回实际观察值和 receipt。调用者不用提供 ghost 源状态、执行成功或逆操作有定义的假设。命令失败时，保留原来的错误和已经完成的成功前缀证书。

## 独立复现

```sh
cargo run -p cordis-kernel --example semantic_context --offline
```

案例运行一个 provider，以及修改 provider 值、创建子组件、发布自身服务的父组件，并检查：

1. 父组件自己的服务值为 42，捕获的 Child 逆操作指向子组件 2。
2. 父组件清理后，provider 的值恢复为 7，子组件 2 被 retire。
3. 一个新父组件可以注册，但其 Child 指令因旧子组件仍保留 provision 而返回 `Conflict`。失败调用不伪造成功和逆操作；此前已经成功的效果仍保留日志。

案例纳入常规开发检查。集成测试还核对真实 provider 身份、XOR 参数，以及越界或无有效资源时的读取。两项负控分别把真实值读取替换为 `None`、把真实逆操作伪造为 Unit；要求 mutant 能编译，然后被对应可执行函数的后置条件拒绝。

## R1 之后的工作

R2 将生产环境的托管插件调用、任意宿主值和宿主协议组合，连接到适用的效果合同；这些不在当前封闭同步解释器的 u64 值理论范围内。R3 推广交错执行和多轮生命周期下的恢复。R4 处理全局调度、终止和适用的合流。

严格 Component 成员资格或成功前缀，不保证之后的每个调用都成功，不保证任意干扰后的每个逆操作都有定义，也不保证异步回调最终返回。

原文的总函数 Component 见证、无限制递归等式以及整篇完成，仍是独立的审计目标。R1 不修改 `check-paper-coverage.py --require-complete`，也不提升这些原文条目的状态。
