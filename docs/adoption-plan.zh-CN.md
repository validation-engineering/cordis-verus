# 采用与形式化方法计划

[English](adoption-plan.md) · 简体中文

本项目希望降低现有 Cordis 应用的维护成本，并把生命周期保证连接到实际运行的代码。
采用需要靠安装、兼容性、诊断和可靠更新来争取。形式化方法通过可审查的合同与证据
支撑这些任务；证明数量本身不能说明项目有用或已被采用。

本文将这些目标落实为有验收条件的工作项。[技术路线图](roadmap.md)保留详细的证明
依赖和宿主工作。[当前状态](status.md)、[论文 ledger](paper-obligations.json)及
[绑定源码的报告](evidence-guide.md)仍是实际结果的来源。本文不修改它们的状态，
也不修改[发布门槛](releasing.md)。

## 首个里程碑服务于谁

首要用户是 Cordis/Harness 插件维护者，以及需要可理解的服务替换、取消与清理行为
的应用开发者。配套的 [cordis-harness](https://github.com/validation-engineering/cordis-harness)
是主要应用入口；小型纯 Rust 示例提供不需要 Node 的路径。Node 是可选的兼容设施，
不是 Rust 内核的必需依赖。[架构说明](architecture.md)区分运行、构建插件与开发
证明所需的依赖。

首次评估应能回答三个问题：能否运行我的任务、能否维护其中的插件、能否检查我依赖的
保证。独立项目经历一次真实修改或故障后仍继续使用，是最重要的采用信号。我们自己的
仓库和示例不计入外部采用。本文不声称已有外部采用。

## 工作项

P0 是独立评估的前置条件；P1 是产品与研究主线；P2 由实际需求触发。这是优先级，
不是交付日期。每项都需要保留文末定义的验收记录。

| ID | 用户目标 | 交付与验收 | 形式化连接 |
| --- | --- | --- | --- |
| **A01 · P0** | 重建某个版本的证据 | 长期可用的固定工具链制品与原始哈希；在声明的平台执行 clean CI；同一冻结版本完成规范负控和打包检查。超时、编译或求解器失败不能算通过。 | F0；既有完整发布门槛继续适用。 |
| **A02 · P0** | 不先学习 Verus 即可运行应用 | 已验收的运行制品和安装说明；独立安装运行官方 Harness 工作流与纯 Rust 示例。不依赖隐藏的相邻仓库、工作区链接或预装验证器；需要编译时明确编译器要求。 | 制品发布依赖 A01；证明复现有单独入口。 |
| **A03 · P0** | 判断已有插件能否迁移 | 修复归档基线的两项非故意差异，保留两项有意合同差异。重跑固定版本的原样套件、官方工作流和实际插件案例；记录改动与回退步骤。 | 兼容缺陷、有意差异和未覆盖行为分开；F1/F3 解释合同依据。 |
| **A04 · P1** | 解释为何未启动或无法完成清理 | 在现有诊断中提供依赖阻塞、owner/episode identity、effect 标签、等待时间和结构化失败。读取诊断不执行用户 callback，不导出服务 payload。 | 是实际状态的观察投影，不是所有执行的证明；随 F1 推进。 |
| **A05 · P1** | JS/Rust 接口只维护一处 | 有版本的接口表示与生成 client/adapter，先覆盖一个 DTO + async 服务。生成代码通过编译及值传递、取消、替换测试；不支持的成员具名报错，不静默生成 `any`。 | 复用既有协议；更强声明等待对应 F1/F2 定理；写明生成器的信任边界。 |
| **A06 · P1** | 依赖声明与 setup 输入保持一致 | 同一声明产生 admission 要求与 typed setup 输入；旧实例退役前准备配置。用编译失败检查和既有生命周期轨迹验收。 | 转换为内核声明和 committed lease；准备阶段不取得生命周期权限。 |
| **A07 · P1** | 保证延伸到真正运行的宿主 | 从共享 Driver/ActionLedger 中消费者清理先于 provider 释放开始；对实际转换建立机械化映射与保持性义务，再扩展到取消、旧代次和并发 action。 | F1；测试和映射文档不能单独完成 refinement。 |
| **A08 · P1** | 更新失败后可预期地恢复 | 在已有 Loader/HMR 路径中说明预检、排空、checkpoint、回滚失败与显式重试。复现恢复失败，保留错误和恢复源。 | 连接 A07；checkpoint 只覆盖声明的状态，不是任意外部 I/O 回滚。 |
| **A09 · P1** | Rust 与 Node 加载同一原生插件 | 提取共享 native loader/controller；同一独立库在两个宿主通过依赖替换、取消、失败保留、checkpoint/retry 场景，并提供可构建模板。 | 同一 ABI 和 journal，遵循 A07 协议；逻辑清理不等于可以安全物理卸载库。 |
| **A10 · P1** | 反复更新的成本可控制 | 按源码、平台与工作负载记录应用延迟、保留资源、tombstone 和加载映像的基线与预算；优化后重跑失败案例。 | 回收仍满足 committed identity、旧 handle 拒绝和失败保留；不预先宣称速度优势。 |
| **A11 · P1** | 审计整篇论文及明确修订 | 按技术路线图推进表示、生命周期和调度依赖。每个 ledger 条目给最终审计结论；反例保留，修订结果单独说明。 | F3；四项整体义务各按自身目标关闭。 |
| **A12 · P1** | 使用有边界、可组合的插件合同 | 定义受管 profile，包含显式依赖、action、owned resource 和可失败 cleanup，提供 SDK、示例与检查。 | F2/F4；任意插件计算、原版 JS callback 和 I/O 不会自动成为已证明部分。 |
| **A13 · P0 → P1** | 复现合同解决的实际问题 | 固定版本的清理顺序、失败保留、迟到结果拒绝及更新失败案例：短演示、可运行复现、合同/证明审查。对比采用等价观察，并保留不利结果。 | 证据只支持实际测试层；内存探针不能说明文件或网络行为。 |
| **A14 · P1** | 在独立项目中验证价值 | 记录真实任务、安装成本、改动及阻塞原因；接入后回访一次真实修改、升级或故障，自愿记录继续使用或退出。 | 用户失败反向指导合同与负控；首轮试用需要有边界的声明，不必等待整篇一般证明完成。 |
| **A15 · P0 → P1** | 不依赖单一作者也能贡献 | 区分兼容、普通宿主和证明贡献入口；快速反馈与完整验收分开；记录语义决策、支持范围和迁移说明，扩大独立审查。 | 合同变更同时更新实现、证明前提和回归。 |
| **A16 · P2** | 在需要时扩展语言或部署边界 | Python、远程 RPC、WASM 等需有真实任务、现有路径不足的证据、维护责任和单独验收；每次扩展一个边界。 | 每个新宿主都有新的环境与失败模型；现有内核证明不自动认证它。 |

兼容起点仍是[归档的 upstream 87/87、native 83/87 结果](evidence/README.md)。
[第二轮](evidence/2026-10-08-a03/README.md)对同一固定版本的原样套件重新运行，
结果为 upstream 87/87、native 85/87，
修复了被测 provider/consumer 更新场景与清理期资源注册错误文本；committed
publication 和 cleanup failure 保留仍是有意差异。历史报告继续保留。这些数量
不代表兼容全部上游版本，也不代表完成 A03 的真实迁移验收。

## 与产品并行的形式化工作

F0–F4 是相关工作层次，不是认证等级或正确性分数。下一座证明桥仍在开发时，可以
在既有保证边界内交付有用的 SDK 改进；不能仅靠测试提升形式化声明。

| 方向 | 要建立的连接 | 完成证据 |
| --- | --- | --- |
| **F0 · 证据可重建** | 源码 → 固定工具 → 证明、负控和测试 → 制品 | 冻结版本通过既有完整门槛；另一环境重建绑定证据。 |
| **F1 · 实际宿主协议** | admission → invocation → landing → drain → cleanup → removal | 对指定的真实转换和公开调用路径建立可机器检查的 refinement，明确前提，包含非空轨迹和负控。 |
| **F2 · 受约束的标准接入** | typed/生成接口 → 共享 owner/generation/resource 协议 | 依赖/方法一致、转换正确、失效能力拒绝；列明外部语言和生成器假设。 |
| **F3 · 生命周期与论文审计** | Component/Child 表示 → 一般恢复 → 调度/进展 → 原文与修订规格 | 81 条均有最终审计结论，完成 whole-lifecycle、corrected-specification、executable-simulation、host-boundary 四项整体义务；保留被反驳的原文声明。 |
| **F4 · 有范围的系统保证** | 发布 API → 共享 Driver → 执行历史 → 适用生命周期规格 | 所选受管 profile 需要的桥都闭合且可独立审查；列明插件、I/O、调度器和工具链假设。 |

受限 F4 profile 可以先于一般 F3 结果完成；缩小范围不能关闭既有整篇义务。
有限前缀安全不代表清理最终完成；进展声明必须写明终止和调度前提。目标是诚实完整
的审计，不是让已有反例的原文命题变真。[论文审查指南](paper-review-guide.zh-CN.md)
展示如何检查已有连接。

## 第二轮：基线中的两项兼容缺口

A03 的两项非故意差异已有受限运行时实现。Cordis profile 允许空 mutation 队列下、
没有托管 invocation 来源的直接外部 provider 更新，与同一同步调用栈内的直接
committed consumer 更新协调。存在 consumer 到 provider 的中间依赖路径、
自定义 `Config` 或 `internal/update` hook 时不加入协调。请求共用生命周期屏障，
等待异步 cleanup/setup，并分别保留自身失败结果。重复 Fiber 更新、事务、
restart/dispose、已排队或跨 microtask 的更新、多跳依赖、自定义配置/hook 以及
Harness profile 仍走原来的 FIFO。详细边界见
[兼容合同](node-compatibility.md#同栈-providerconsumer-更新)。

清理期资源注册错误现在包含 `inactive context`，同时保留 `CLEANUP_BLOCKED` code
和优先执行的 `STALE_EPISODE` 拒绝。这些改动没有证明整个 JS 协调器或任意 callback，
没有关闭论文的 host-boundary 义务。

A03 仍需真实插件迁移记录，包括所需改动与回退步骤。A04 的四种诊断任务已有下述
受限实现。A05 的 DTO + async 生成器与关联 A07 宿主切片应从一个真实服务开始；
实际外部阻塞可以调整顺序，但不能删除证明依赖。

## 第三轮：诊断与运行产物交付

A04 已导出 shared Driver 的依赖原因、真实 target/committed binding、consumer/child
屏障和 pending action ticket。Node 增加带标签的保留 inverse 身份、尝试次数、失败和
可选经过时间，以及结构化旧 episode 拒绝信息。快照读取不执行 callback，不重试或
释放资源。回归同时修复嵌套 effect 的显式重试，以及同一原始 callback 多次注册时
精确保留失败的那一次。范围见[宿主诊断](host-diagnostics.zh-CN.md)，其中明确区分
普通 Rust 的清理合同。外部真实排障记录与宿主 refinement 仍是独立工作。

A01/A02 的交付支持新增按平台打包的预编译 npm 产物、独立新项目安装器和可选的
GitHub draft prerelease 创建流程。工作流默认选择 Linux x64 和 macOS Apple Silicon，
设置 `include_macos_intel=true` 可加入 macOS Intel；所有选定平台的完整质量门槛与
产物安装/重装全部通过后才创建草稿，产物和验证声明仅覆盖这些平台。使用运行库需要 Node/npm 和 GitHub 访问，不需要 Rust、Verus
或源码 checkout。这是 Node 兼容运行库，不是完整打包的 Harness 应用或纯 Rust 应用
可执行文件。当前尚无 runtime release；[分发指南](native-distribution.zh-CN.md)说明
已准备的安装路径和维护者的发行验收方式。

## 独立安装验收

在宣称 M0 或可用发行包之前，保留来自维护者工作区和构建缓存以外的记录：

1. 记录源码版本、制品哈希、OS/架构，以及运行时或编译器版本。区分源码试用与
   制品安装。
2. 从干净用户环境开始：没有相邻仓库、工作区符号链接、自定义 addon 覆盖或隐藏的
   预装验证器。运行制品不能要求 Verus；源码构建必须列出所有实际前置依赖。
3. 仅按文档路径执行。使用明确的离线脚本模型 provider 运行受支持的官方 Harness
   默认工作流，并运行文档中的纯 Rust 示例；确认 Rust 路径无需安装 Node。
4. 移除并重装交付制品，再次运行任务并记录缺失或不支持目标平台的错误。保留命令、
   输出、耗时和维护者介入，标明冷/热缓存条件。
5. 记录评估结论和未解决阻塞。维护者本机打包检查或配置好的 CI 矩阵不能完成独立
   采用验收；平台声明需要每个所述平台的实际运行。

这是验收要求，不是声称已有合格制品。公开实验性源码与发行运行包是不同里程碑；
两者都不能撤销既有安全或发布政策。

## 任务接入、贡献与衡量

真实迁移或维护任务使用采用表单。可以用最小公开复现代替私有源码；不要提交凭据
或私有 prompt。记录当前做法、目标行为、环境、基线步骤，以及决定继续或退出的
条件。不要求默认遥测。issue 是任务证据，不等于授权将个人或项目名称用于宣传。

小型行为差异使用[缺陷表单](../.github/ISSUE_TEMPLATE/bug_report.yml)，合同或论文
缺口使用[证明表单](../.github/ISSUE_TEMPLATE/proof.yml)，新边界使用
[功能表单](../.github/ISSUE_TEMPLATE/feature.yml)。检查要求见
[贡献指南](../CONTRIBUTING.md)。局部检查用于开发反馈，发布仍须执行完整门槛。

每项工作或语义变更应保留：

1. **任务与合同**：谁需要什么、可观察的成功/失败行为，以及失败后保留的内容。
2. **范围与连接**：profile、版本、平台和假设；真实 API/Driver/内核路径；对应证明
   与未验证边界。
3. **证据**：非空成功执行、失败/负控、兼容结果，以及真实应用路径的源码绑定记录。
4. **采用与责任**：安装/修改/排障成本、评估反馈、支持责任和下一个未解决条件。

按平台记录首次运行尝试与成功、迁移改动、维护者介入，以及真实修改后是否继续使用。
也记录独立合同审查、反例复现和其他项目对方法的复用。Stars 和下载量只是背景，
不能替代这些观察。保留实际样本及选择其他方案的理由；不能从未观测的竞品使用量
推断市场排名或增长目标。
